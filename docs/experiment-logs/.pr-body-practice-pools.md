**TL;DR.** The per-skill practice-pool breakdown (`SamplerConsultation`, #119) had never been run on `tossingroomsplit` — the domain the reset-free result rests on. It is now. **Tossing Room is clean, and clean in the specific way Tossing3D was not.** All five `param_dim = 0` skills fall entirely in `NO_SAMPLER` — **23,863/24,750** of all practice executions — but every one of them succeeds on **every** execution (`MoveRoom` 19098/19098, `PressRecycling` 3576/3576, `PickupTrash` 751/751, `PressTrash` 277/277, `PickupRecycling` 161/161), so nothing is learnable **and nothing needs to be**. Both throws carry a real parameter and are graded on an add-effect that genuinely fails. The counts **coincide exactly with PR #90's published numbers**, reached from a different instrument.

**The more important finding is about an instrument now on `main`, not about the domain.** #127's decision rule assigns `ThrowRecycling` to **inability** here, and that verdict is **wrong**: its `inability` cell has no power requirement and no plateau check, so at `I = 56` it fires on a sampler that is merely early. Recycling's informed successes are still *rising* when the budget ends — `0, 0, 2, 3, 6` by fifths of the run. A rule on `main` gives a wrong answer on this project's main domain. See Recommendation.

## Question / goal

Split every practice execution on `tossingroomsplit` into its four `SamplerConsultation` pools, per lifted skill, and decide for each skill which diagnosis applies: *there was never a parameter to learn* (`NO_SAMPLER`), *the success predicate cannot discriminate* (`UNINFORMATIVE`), or *the classifier ranked candidates* (`INFORMED`). This machinery has been run on Light Switch, Ball-Ring (#126) and Tossing3D (#127), and never here.

## Background

`SamplerConsultation` was split in #119 so that "no sampler exists or ever can" (`param_dim == 0`) is told apart from "a sampler exists, was consulted, and could not discriminate". Before #119 both were one "fallback" number, and that conflation is how a Tossing3D design flaw survived two experiments: `Toss` (`param_dim = 0`) and `MoveToThrowPose` (`param_dim = 1`, add effect `NearBin` satisfied by every standoff its sampler could draw) rendered identically. #127 then showed EES cannot learn Tossing3D's standoff at all, because it is graded on the wrong label — the sampler almost never sees a negative, so it never has two classes to separate.

The remedies are opposite, which is why the split matters: `NO_SAMPLER` means the domain is decomposed wrong; `UNINFORMATIVE` means the success predicate is too permissive.

## Hypothesis

Tossing Room is structurally clean: five of seven skills are `param_dim = 0` and only the two throws carry a parameter, graded on the item landing in the bin — an effect that genuinely fails, so the label set is genuinely two-class. **"I expect it's clean" is exactly what everyone assumed about Tossing3D**, so both halves were verified against the source before any result was read.

## Methods

Both published arms, matched exactly from their committed reproduction commands. Fixed seeds 0-9 via `scripts/run_sweep.py`, never drawn; `--num-test-tasks 30` (14 TRASH / 14 RECYCLING / 2 EMPTY); `--max-workers 10`; inside `systemd-run --user --scope -p MemoryMax=16G -p OOMPolicy=continue`.

| arm | source | protocol | transitions/seed |
|---|---|---|---|
| standard | `2026-08-05-tossingroomsplit-throw-rates.md` | `--num-cycles 25 --max-steps-per-interaction 100` | 2,500 |
| 10x | `2026-08-06-tossingroomsplit-10x-budget.md` | `--num-cycles 250 --max-steps-per-interaction 100 --exploration-epsilon 0.5` | 25,000 |

The **standard** arm is primary: it is the budget every published `tossingroomsplit` headline is a statement about, so a breakdown taken there is comparable with #90's numbers and checks the instrument against a known answer.

**The structural claims, verified against the source rather than repeated.** `param_dim` in `src/hitl_pmp/environments/tossingroomsplit/skills.py` is 0 for `PickupTrash`, `PickupRecycling`, `MoveRoom`, `PressTrash`, `PressRecycling` and 1 for `ThrowTrash`, `ThrowRecycling` — already pinned by `tests/environments/tossingroomsplit/test_skills.py`.

**What the throws are graded on** is the #127 question, and it had to be answered from the dynamics. Each throw has two add-effects, `TrashInBin(trash, trash_bin)` and `HandEmpty(robot)`, and `EesMethod.observe_pending` labels a success iff **all** add-effects hold (`success = self._pending.add_effects <= true_atoms`). In `TossingRoomSplitEnvironment._apply_throw` the item is released **unconditionally** — `next_state.set(obj=self.robot, feature_name="holding", feature_val=0.0)` sits outside every branch — so `HandEmpty` always becomes true and **carries no information**. The bin count increments **only** when `robot_room == bin_room and abs(raw_force - required) < self.throw_tolerance`, and the room term is pinned by the skill's own `TrashBinInRoom` precondition. So the discriminating add-effect is `TrashInBin`/`RecyclingInBin`, and it is a genuine function of the sampled force. **This is the precise inverse of Tossing3D's defect**, where the graded effect was satisfied by every parameter the sampler could draw.

The primary table comes from `practice_diagnostics.py` on `main`, unmodified. The two derived tables come from `analysis/practice_makes_perfect/tossingroomsplit_practice_pools.py`, added here with two tests.

Every row's four pools sum exactly to its attempts (asserted). Aggregate: **23,863/24,750** `NO_SAMPLER`, **367/24,750** `EPSILON_RANDOM`, **357/24,750** `INFORMED`, **163/24,750** `UNINFORMATIVE`. The pools sum to 24,750 against a 25,000 budget — short by exactly **250 = 25 cycles x 10 seeds**, one unobserved execution per practice period, which is `EesMethod`'s documented deviation 2. Nothing is silently dropped.

### The domain is clean, on three checks Tossing3D failed

1. **Every `NO_SAMPLER` execution is a skill that never fails** — all five are at `succeeded == attempts` exactly, across 23,863 executions. A skill with no sampler is only a defect if its outcome depends on something a sampler could have chosen. Tossing3D's `Toss` was `param_dim = 0` **and failed**.
2. **Both throws are genuinely two-class** — 293/727 and 33/160, nowhere near a degenerate label.
3. **`UNINFORMATIVE` is a warm-up transient, not a permissive predicate** — by fifths, `ThrowTrash` 84, 32, 0, 0, 0 and `ThrowRecycling` 22, 16, 6, 0, 3. A permissive predicate holds it flat and high forever; this decays as labels accumulate.

### Informed draws against each throw's own epsilon-random control

| skill | informed | epsilon-random | delta | Fisher exact two-sided |
|---|---|---|---|---|
| `ThrowTrash` | 208/301 | 61/310 | **+49.43pp** | **p < 0.0001** |
| `ThrowRecycling` | 11/56 | 11/57 | +0.34pp | p = 1.0000 — **null result** |

**These coincide exactly with PR #90's published counts, reached from a different instrument** — #90 read them from `scripts/tossingroomsplit_skill_traces.py`, a bespoke collector subclassing `EesMethod`; this reads them from `stats.json`'s domain-agnostic pool tally. Two independent paths to the same four counts is a check on both, and confirms nothing merged between #90 and `ebf3d92` moved this domain's dynamics or sampler. No published number was edited or recomputed.

### The decision rule on `main` returns a false verdict here

The rule carried over from #127 (fixed in this experiment **before any result was read**) assigns `ThrowRecycling` to **inability**: `I/A = 56/160 = 0.35 >= 0.30`, and `IS/I = 11/56 = 0.196` sits within ±0.10 of its epsilon-random reference `11/57 = 0.193`.

The same run contains the evidence against that verdict:

| `ThrowRecycling`, by fifth | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| informed attempts | 0 | 3 | 16 | 21 | 16 |
| informed successes | 0 | 0 | 2 | 3 | 6 |
| uninformative attempts | 22 | 16 | 6 | 0 | 3 |

The classifier is not consulted at all until the third fifth, and its informed successes are **still climbing when the budget runs out** — the starvation signature, not inability. The defect is in the rule: **`I/A >= 0.30` is a statement about the share of draws that were informed and says nothing about whether `I` is large enough to detect an effect.**

## Recommendation

1. **Tossing Room needs no fix.** The reset-free result does not rest on a mis-graded skill. This is the answer the audit was for, and it is a clean one.
2. **Amend #127's decision rule before it is used again** — it is on `main` and it returns a false verdict on this project's main domain. It needs two things it does not have: a **power requirement** on the `inability` cell (an explicit MDE from `I` and the control's size, so a cell cannot fire when the test could not have detected the effect), and a **plateau check** (inability requires the informed-success curve to have flattened; a curve still rising at the final window is starvation by construction). I have not changed the rule — it is Josh's call.
3. **Fix the two tests failing on `main`.** `test_tossing3d_practice_diagnosis.py` has two fixtures that #119's validator rejects. Proven not mine: this branch's `src/`, `tests/`, `analysis/` and `scripts/` are byte-identical to `main`'s. Reported, not fixed.
4. **Land #126, then re-read this page's `NO_SAMPLER` column.** The pool tally counts *executions*, and EES executes a chosen candidate's whole prefix, so `MoveRoom`'s 19098/19098 is **not** evidence that EES chose to practice `MoveRoom`. There is a code-level prediction #126 can check: `EesMethod.score_ground_skill` returns `-math.inf` when `skip_perfect and measured_success_rate(...) == 1.0`, and `skip_perfect` defaults to `True`, so all five `param_dim = 0` skills should show up almost entirely as `declined_perfect`. Nothing on `main` can test that.
