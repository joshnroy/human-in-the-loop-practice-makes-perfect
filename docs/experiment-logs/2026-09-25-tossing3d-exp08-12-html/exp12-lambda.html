EXP-12: choosing λ (practice-cost weight), both competence models

Code: fix (b), PR #372 @ 5c5a4b6f on #370. Grid engine, 50 cycles × 20 actions, ε = 0.5, human reset cost 5, non_epsilon evidence, seeds 0–2 for arms whose seed 0 peaked at ≥ 5/10 (Model A λ ≥ 1e-4 has seed 0 only). Decision view below is seed 0 only (as pre-registered); the per-seed figure adds seeds 1–2. Colour encodes λ (sequential), not the project's arm-role colour, since every arm has the same mechanism.

Bimodal across seeds — which reset skill, not whether the human is needed. At λ > 0, seeds 0 and 1 switch almost entirely to the second reset skill (non_human_reset, which is also executed by the human at cost 5), while seed 2 keeps using ask_for_reset. Total resets still differ: at Model A λ ≤ 3e-6, seeds 0–1 total 100–117 against 143–161 for seed 2 — that is why seed 2 spends ~1.5× the practice cost. Eval is not bimodal (e.g. Model A λ = 3e-6: 7.6 / 8.4 / 8.4). All 3187 resets put the bin on the robot side (the EXP-12 code forced it).

Correction. The earlier figure and table in this place counted only ask_for_reset and mis-paired each reset with a bin pose, so its robot-side / opposite-side split was wrong. They are replaced here. Two things change: (1) EXP-12 forced practice resets to the robot side, and with correct pairing 0/3187 resets across all 37 runs put the bin on the opposite side (3187/3187 robot side, 0/3187 not observed because the reset was the last action of its cycle). (2) non_human_reset_cube_bin_only is a relabelled human reset in this code (same cost 5, executed by the human oracle, counted as a human intervention), so it is counted here too. In every λ > 0 arm run with 3 seeds except Model B λ = 3e-3 (which barely resets at all), seeds 0–1 did not stop needing resets: they call ask_for_reset only 4–7 times and take the rest (31–116 per run) through the second reset skill; seed 2 does the reverse. The bimodal-seeds note above, which says seeds 0 and 1 "almost stop asking for human resets", counts only ask_for_reset and should be read with this in mind.

Method: resets are the dispatch/outcome pairs in pomdp_decisions.jsonl inside each practice cycle (session_start → refit). The side is read from the first tick of the next skill block in the same cycle in tossing3d_state_log.jsonl (barrier at x = 1.3; robot side x < 1.3). Reset dispatches without an outcome: 1 (the final, crashed cycle of the failed run local_trend λ = 1e-5 seed 1; not counted). Failed reset outcomes: 0.
