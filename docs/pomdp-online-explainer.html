Tossing3D · POMDP walkthrough
01 · Purpose

Is another practice action worth doing?

The robot chooses between practicing an available skill, asking for a human reset, and stopping to use what it has learned.

It reasons about the current physical state, uncertainty about skill success and improvement, and the remaining practice budget. The objective is predicted deployment success after practice—not simply getting a successful practice throw.

Observe state→Search possible futures→Execute one skill→Observe outcome and replan

This describes implementation snapshot 51b2721 and the seed-0 H=B=10 / H=B=100 validation runs. Earlier videos with fixed PickCube and OpenGripper used a different model.

02 · State and belief

The world is observed; skill parameters are uncertain.

The symbolic physical state s distinguishes situations such as ready to pick, holding the cube, gripper closed, stranded, and solved. The hidden quantity is each robot skill’s parameter vector:

The search state also carries accumulated cost C and pending practice-example counts for each skill. Those counts matter because actual sampler refits happen at session boundaries.

03 · Initialization

No robot skill starts with fixed competence.

p ∈ {0, 0.25, 0.5, 0.75, 1}
η ∈ {0, 0.1}
ba(p,η) = 1/10 for each of the ten pairs

All three robot skills start with independent copies of this prior. Each initial mean competence is 0.5; the prior probability of η=0 is 0.5.

The endpoints allow evidence to support always-successful or always-failing stationary behavior. They are possible hypotheses—not assigned outcomes for a particular skill.

This is still a finite, hand-chosen hypothesis family. Learning its weights does not make its coverage or calibration guaranteed. The older toss prior used only p ∈ {0.25, 0.5, 0.75}; these new runs use the expanded grid.
04 · Bayes update

Success and failure reweight the hypotheses.

b′a(p,η) = ba(p,η) · py(1−p)1−y / Z
y = 1 for success; y = 0 for failure

Z normalizes the weights. A success favors higher p; a failure favors lower p. Only the skill that produced the observation is updated.

PickCube and OpenGripper supply evidence on every observed practice attempt. Toss’s greedy-policy outcomes update its competence posterior; random exploration outcomes do not, because they were generated by a different parameter-selection policy. Toss training rows can still be collected from exploration.

Held-out evaluation outcomes are not used as training data.

The update uses current p, not η directly. Distinguishing learning rates requires observations after hypothesized improvement has taken effect across session boundaries.
05 · Learning-curve forecast

A predicted improvement is not a controller update.

p after n examples = 1 − (1−p)(1−η)n

For p=0.5 and one example: η=0 predicts 0.5; η=0.1 predicts 0.55. The posterior averages across such possibilities.

At STOP evaluation, the model projects pending examples through this formula. At the real session boundary it advances the hypotheses; later outcomes can favor improving or stationary hypotheses.

Toss

Has a real trainable parameter sampler. Its refit uses collected training rows.

Pick and OpenGripper

Remain parameter-free controllers. Their learning curves are hypotheses to test against data—not changes to their execution code.

One-session limitation: these validation runs test data flow and planning behavior. They do not provide post-refit practice observations with which to establish η≈0 for Pick/Open. At p=1, all η predict zero further improvement, so η itself is unidentifiable.
06 · Terminal value

STOP asks: “How good would deployment be now?”

evaluate_policy computes g(θ), the predicted probability of solving a fresh deployment task under the sampled skill competences. Human reset is unavailable during this modeled deployment.

G(C,θ) = g(θ) if C ≤ B; otherwise −∞
J(C,b) = Eθ∼b projected through pending examples[G(C,θ)]

G is the ROI–cost function. These runs use its hard-budget version. The implementation filters out actions that would exceed B, so it never needs to pass −∞ through the numerical solver.

The older linear version was G(C,θ)=g(θ)−λC. That penalty is inactive whenever a hard budget is configured. Within budget, there is no extra reward for leaving budget unspent; STOP wins exact ties.

07 · A different horizon

Deployment lookahead stays at four skills.

The deployment horizon D=4 is not the practice search horizon H, nor the real evaluation episode limit. It is the surrogate evaluator’s lookahead.

For sampled Pick competence q, Toss competence t, and Open competence r, the modeled successful paths within four actions are:

  1. Pick succeeds → Toss succeeds: probability qt.
  2. Pick fails → Open succeeds → Pick succeeds → Toss succeeds: probability (1−q)rqt.
g(θ) = qt[1 + (1−q)r]   when D=4

This is evaluated for each sampled joint θ—not by substituting the mean competence of every skill into a nonlinear expression.

D=4 is an existing modeling choice, not a demonstrated sufficient deployment horizon. Increasing H does not fix or increase D.
08 · Inside one search

Compare stopping against every affordable action.

solve_belief_space_expectimax(s, C, b, h):
    θ[1..N] ← sample_theta_from_belief(b)
    J ← mean(score_pomdp_value_from_policy_value_and_cost(
                 evaluate_policy(θ[i]), C))
    best_value, best_action ← J, STOP
    if h == 0: return best_value, best_action

    for a in get_valid_actions(s):  # applicable AND within budget
        Q(a) ← 0
        for (s′, c) in sample_next_states(s, a, b):
            b′ ← update_belief_state(b, s, s′, a)
            V′ ← solve_belief_space_expectimax(s′, C+c, b′, h−1).value
            P ← transition_probability(s′, c, s, a, b)
            Q(a) ← Q(a) + P × V′
        if Q(a) > best_value:
            best_value, best_action ← Q(a), a
    return best_value, best_action

This is a condensed rendering of the implemented function names. It is a max over actions and an expectation over their outcomes: expectimax.

Successful and failed Pick/Open outcomes use their current belief means as predictive probabilities and condition the corresponding posterior in each branch. The human reset branch is deterministic in the model.

09 · Approximation and caching

100 parameter samples per unique search state.

N=100 controls the Monte Carlo estimate of STOP utility at each state. Each sample is a joint draw of Pick, Toss, and OpenGripper parameters.

It is not 100 physical trials, 100 sampled full trajectories, or 100 branches. Despite its name, sample_next_states enumerates the finite successor model here, merging identical successors. Their probabilities are then summed exactly.

Repeated identical search arguments share a cached result within a search. The next real decision creates a fresh search and a fresh cache, with new parameter draws.

Values remain noisy. Maximizing sampled estimates can favor actions that offer no true learning benefit. More samples reduce noise but do not eliminate model error or the bias introduced by maximizing noisy values.
10 · Real execution

Execute one skill—not the entire imagined plan.

  1. Read the actual symbolic state and current belief.
  2. Run a fresh H-step search using the total cost already spent.
  3. Execute only the selected skill and charge its cost.
  4. Observe success/failure, update evidence and pending examples, then replan.
  5. If STOP is selected, finish the practice session and process its boundary update.
Replanning refreshes H.
Replanning does not reset C or replenish B.

Each new practice session starts at C=0 with a fresh B, retaining learned samplers and beliefs. Human resets within a session still consume its budget.

With B=10 and unit costs, ten paid actions use the entire budget. Decision 11 can choose STOP; it does not need to wait for the 150-step outer cap.

reset=never disables automatic practice resets. It does not disable the selectable, charged human reset skill.

12 · Limits and cost

Affordable depth is not computational feasibility.

Effective remaining depth ≤ min(H, ⌊(B−C)/cmin⌋)
Here cmin=1, so depth ≤ min(H, B−C).

This bound concerns a search decision. The outer session cap additionally limits real execution, but is not itself passed as the search horizon.

The depth cutoff is still present. Python’s interpreter recursion limit was raised only to support the requested depth—not to remove the algorithmic horizon.

The search expands outcome branches and changing beliefs at many levels. Memoization helps only when arguments match. Full diagnostics also retain every parameter sample until the root decision completes.

H=100 may exhaust its memory cap before producing a single action. “No time cutoff” is not “unlimited memory,” and no video can show practice before the first action has been chosen.
13 · Outputs

Distinguish predicted value from observed learning.

Displayed improvement potential = maxpractice action a Q(a) − J(STOP)

Positive favors continuing; negative favors stopping. This is the best action’s expected downstream advantage, including possible later practice—not the learning rate η of that action.

Competence bars show current posterior means before the pending-example projection. STOP utility uses projected post-session beliefs, so it need not match a simple calculation from those bars.

“No affordable/applicable practice action” means there was no candidate to compare with STOP. At C=B, it means budget exhausted—not proof that additional practice would have zero benefit.

The HTML tree contains the complete recorded search at the STOP decision, including sampled θ values, costs, probabilities, contributions, and cached successor evaluations. It is not a concatenation of every earlier decision’s tree. The JSONL retains those earlier decisions.

14 · Interpretation

A validation run, not yet a learning-curve conclusion.

Check that each action is followed by replanning, costs accumulate correctly, robot-skill beliefs respond to data, STOP is selected when appropriate, and the saved tree explains the decision.

Look for repeated resets, poor state predictions, inconsistent outcome labels, or large disagreements between modeled competence and execution. These are diagnostic findings—not things to explain away with a better evaluation score.

One seed and ten evaluation tasks are insufficient to establish a reliable improvement. Even a no-practice run can get different before/after scores because evaluation execution is stochastic. No significance claim is made here.

The most important distinction: we are testing whether the system estimates and acts on learning potential coherently—not assuming that every robot skill truly improves.
